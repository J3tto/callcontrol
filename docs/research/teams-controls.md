# Driving new-Teams in-call controls from outside the client on macOS

Research for issue #4. Scope: toggle mute, toggle camera, raise/lower hand, send a reaction, from a Swift helper spawned by the Stream Deck plugin, ideally without stealing focus. Microsoft retired the legacy third-party meeting/call control API on 30 June 2026 (MC1266901, [mirror](https://mc.merill.net/message/MC1266901)); nothing below depends on it.

## 1. What Teams itself offers

### Keyboard shortcuts (Microsoft's page, Mac tab, "Meetings and calls")

Source: [Keyboard shortcuts for Microsoft Teams](https://support.microsoft.com/office/2e8e2a70-e8d8-4a19-949b-4c36dd5292d2). Columns are "Mac" and "Web" on the macOS tab, "Desktop app" and "Web app" on Windows.

| Action | Mac | Mac web | Windows desktop | Windows web |
|---|---|---|---|---|
| Toggle mute | ⌘⇧M | ⌘⇧M | Ctrl+Shift+M | Ctrl+Shift+M |
| Toggle video | ⌘⇧O | ⌘⇧O | Ctrl+Shift+O | No shortcut |
| Raise or lower your hand | ⌘⇧K | ⌘⇧K | Ctrl+Shift+K | Ctrl+Shift+K |
| Temporarily unmute | ⌥Space | ⌥Space | Ctrl+Space | Ctrl+Space |

The page notes the temporary-unmute key only works after "Settings > Privacy > Keyboard shortcut to unmute" is switched on. **No meeting-reaction shortcut exists on any platform**; the only reaction entry is "React to the last message" (⌥⌘R on Mac), which is for chat. Microsoft's [live reactions page](https://support.microsoft.com/en-US/teams/meetings/express-yourself-in-microsoft-teams-meetings-with-live-reactions) says to "select React in the meeting controls" and pick Like, Love, Applause, Laugh or Surprise; it mentions no shortcut. Reactions therefore require opening the React menu.

Every shortcut is a toggle; there is no "set muted" key.

### URL scheme and local command paths

Microsoft's [deep-link docs](https://learn.microsoft.com/en-us/microsoftteams/platform/concepts/build-and-test/deep-link-workflow) list `msteams:/l/...` and `https://teams.microsoft.com/l/...` links only for starting chats, opening the scheduling dialog, starting a call, sharing to stage, the meeting side panel, and joining a meeting. Nothing controls an in-progress call. The only local command path was the retired WebSocket API ("Settings > Privacy > Manage API"); the [Raycast extension](https://github.com/raycast/extensions/blob/main/extensions/microsoft-teams-calling/src/teams/meetingClient.ts) shows what it offered (`toggle-mute`, `toggle-video`, `toggle-hand`, `react-like/love/applause/laugh/wow`, `query-meeting-state`) and its [changelog](https://github.com/raycast/extensions/blob/main/extensions/microsoft-teams-calling/CHANGELOG.md) (last entry 2026-06-28) still targets it, so it is dead with the API. No replacement is documented.

## 2. Delivering shortcuts

**CGEvent.post(tap:)** "Posts a Quartz event into the event stream at a specified location" ahead of any taps there ([Apple](https://developer.apple.com/documentation/coregraphics/cgevent/post(tap:))). The event goes wherever the window server routes keyboard input, i.e. the frontmost app, so Teams must be activated first.

**CGEvent.postToPid(_:)** (macOS 10.11+) has no description at all in Apple's reference ([Apple](https://developer.apple.com/documentation/coregraphics/cgevent/posttopid(_:))). Field reports are mixed and unanswered: one developer found it "working just for application, which owns menu bar" ([thread 695941](https://developer.apple.com/forums/thread/695941)); another still had to focus Logic for a dialog to react ([thread 724835](https://developer.apple.com/forums/thread/724835)). Hammerspoon's `event:post(app)` is `CGEventPostToPSN` ([libeventtap_event.m](https://github.com/Hammerspoon/hammerspoon/blob/master/extensions/eventtap/libeventtap_event.m)), and several Teams-mute configs rely on it to send ⌘⇧M without activating ([eddy-geek](https://github.com/eddy-geek/hammerspoon/blob/master/mute_teams.lua), [justintout](https://github.com/justintout/.hammerspoon/blob/master/teams.lua)), while others activate first ([levinine](https://github.com/levinine/hammerspoon-config/blob/master/teams-toggle-mute.lua)). Whether a pid-targeted ⌘⇧M reaches new Teams' web content while another app is frontmost is **unverified** and is the first thing the spike must test.

**AppleScript / System Events `keystroke`** is what most published scripts use, and all of them `activate` Teams first, send the key, then re-activate the previous app ([sammcj](https://github.com/sammcj/scripts/blob/master/macos/applescripts/ms-teams-mute-toggle.applescript), [nocksock](https://github.com/nocksock/dotfiles/blob/master/scripts/.vault/ms-teams-toggle-audio.applescript), [Yank](https://github.com/lanewinfield/yank/blob/main/macos-app/YankCompanion/Actions/ActionExecutor.swift), [solintllc](https://github.com/solintllc-robert/mac_automation/blob/master/mute-unmute-conference-calls.applescript)). Two of them cycle Teams windows with ⌘` because the shortcut only lands in the meeting window; a [Keyboard Maestro thread](https://forum.keyboardmaestro.com/t/muting-a-microsoft-teams-call/36291) reports the same ("only works if the focus is on the window for the call"). This route always steals focus for a moment.

**Permissions.** `CGEvent.h` documents `CGPreflightPostEventAccess` as "Checks whether the current process already has event synthesizing access" and `CGRequestPostEventAccess` as "Requests event synthesizing access if absent, potentially prompting"; `CGRequestListenEventAccess` is the separate listen (Input Monitoring) grant ([SDK header](https://github.com/phracker/MacOSX-SDKs/blob/master/MacOSX11.3.sdk/System/Library/Frameworks/CoreGraphics.framework/Versions/A/Headers/CGEvent.h)). Apple's user docs describe Accessibility as letting an app "access and control your Mac" ([Apple](https://support.apple.com/guide/mac-help/allow-accessibility-apps-to-access-your-mac-mh43185/mac)) and Input Monitoring as letting it "monitor your keyboard, mouse, or trackpad" ([Apple](https://support.apple.com/guide/mac-help/control-access-to-input-monitoring-on-mac-mchl4cedafb6/mac)). Posting needs only the Accessibility grant (the header does not name the pane; that the post-access prompt lands in Accessibility is observed behaviour, not documented). AppleScript additionally needs the Automation grant ([Apple](https://support.apple.com/guide/mac-help/control-access-to-apps-automation-mchl07817563/mac)) and `NSAppleEventsUsageDescription` in the helper's Info.plist ([Apple](https://developer.apple.com/documentation/bundleresources/information-property-list/nsappleeventsusagedescription)), so it is strictly more permission surface than CGEvent for no gain.

## 3. Accessibility actions

`AXUIElementPerformAction` "Requests that the specified accessibility object perform the specified action"; `kAXPressAction` "Simulates a single click, such as on a button" ([Apple](https://developer.apple.com/documentation/applicationservices/1462091-axuielementperformaction), [Apple](https://developer.apple.com/documentation/applicationservices/kaxpressaction)). Apple warns the call can return `kAXErrorCannotComplete` on timeout, which "does not necessarily mean that the function has failed", and suggests retrying or raising `AXUIElementSetMessagingTimeout`. Trust is checked with `AXIsProcessTrustedWithOptions` and `kAXTrustedCheckOptionPrompt` ([Apple](https://developer.apple.com/documentation/applicationservices/1459186-axisprocesstrustedwithoptions)). Only the Accessibility grant is needed.

Apple does not document AXPress on web content, but both engines implement it without a frontmost check: WebKit dispatches `accessibilityPerformPressAction` to the main thread and calls `AccessibilityObject::press()`, which hit-tests and fires a simulated click under a user-gesture indicator ([WebAccessibilityObjectWrapperMac.mm](https://github.com/WebKit/WebKit/blob/main/Source/WebCore/accessibility/mac/WebAccessibilityObjectWrapperMac.mm), [AccessibilityObject.cpp](https://github.com/WebKit/WebKit/blob/main/Source/WebCore/accessibility/AccessibilityObject.cpp)); Chromium's `accessibilityPerformPress` runs `DoDefaultAction` when the node has one and is not restricted ([browser_accessibility_cocoa.mm](https://github.com/chromium/chromium/blob/main/ui/accessibility/platform/browser_accessibility_cocoa.mm)). Menu items in the React menu are ordinary web buttons/menuitems, so the same action applies, but the menu must be opened (AXPress on "React") before its items exist.

Which engine new Teams for Mac embeds is **unverified**: Microsoft's [system requirements](https://learn.microsoft.com/en-us/microsoftteams/teams-client-system-requirements) list "Webview2" under the macOS client, and one shipping tool notes Teams' mic capture may show up under a `com.apple.WebKit` process ([MeetingSquelch CallApps.swift](https://github.com/ForITLLC/MeetingSquelch/blob/main/Sources/CallApps.swift)). The spike should list `Microsoft Teams.app/Contents/Frameworks`.

The real risk is tree exposure. Multiple reports say new Teams exposes its AX tree inconsistently, sometimes only while Accessibility Inspector or VoiceOver is running ([Apple forums 763286](https://developer.apple.com/forums/thread/763286), [756895](https://developer.apple.com/forums/thread/756895), [Tech Community](https://techcommunity.microsoft.com/discussions/teamsdeveloper/enable-accessibility-tree-on-macos-in-the-new-teams-work-or-school/4033014); no Microsoft answer). Electron documents `AXManualAccessibility` as the attribute assistive tools set to switch the tree on ([Electron](https://www.electronjs.org/docs/latest/tutorial/accessibility)); Chromium-based apps react to `AXEnhancedUserInterface`. Two 2026-era tools that work against new Teams set one of these before searching: MeetingSquelch sets `AXManualAccessibility`, finds the mic button by label (`"⇧ ⌘ M"`, `"unmute"`, `"mute mic"`), ranks windows titled "Microsoft Teams Call", "Meeting compact view", "Sharing toolbar" above "Main Window", keeps a `teamsIgnoresPress` flag for presses that returned success but did nothing, and falls back to the shortcut when the toolbar is hidden ([CallApps.swift](https://github.com/ForITLLC/MeetingSquelch/blob/main/Sources/CallApps.swift), [AX.swift](https://github.com/ForITLLC/MeetingSquelch/blob/main/Sources/AX.swift)); meeting-notes sets `AXEnhancedUserInterface`, identifies the meeting window by a "Leave" button and reads mute state from `"Mute mic"` / `"Unmute mic"` titles (also German) ([TeamsMuteReader.swift](https://github.com/SyntaxFisher/meeting-notes/blob/main/TeamsMuteReader.swift)).

## 4. Idempotency and confirmation

Shortcuts are blind toggles. The only confirmation mechanism left is reading the control's AX label/value before and after: MeetingSquelch's `awaitFlip` polls the label and notes "Teams relabels within ~15 ms of a press that took". The retired API's `query-meeting-state` has no successor. Camera and hand labels (e.g. "Turn camera on/off", "Raise hand"/"Lower hand") are **unverified**; reactions have no persistent state, so they are fire-and-forget and can only be confirmed by the React button becoming pressable.

## 5. Recommendation

| Control | Primary | Fallback | State read |
|---|---|---|---|
| Mute | AXPress mic button in meeting window | focus-swap + ⌘⇧M | AX label Mute/Unmute mic |
| Camera | AXPress camera button | focus-swap + ⌘⇧O | AX label (verify) |
| Hand | AXPress raise-hand button | focus-swap + ⌘⇧K | AX label (verify) |
| Reaction | AXPress "React", then AXPress item | none without a shortcut | n/a |

Permissions: one Accessibility grant covers AX and CGEvent posting; avoid AppleScript (adds Automation). The grant attaches to the responsible process and its code signature, so sign the helper stably (Apple's [TN3127](https://developer.apple.com/documentation/technotes/tn3127-inside-code-signing-requirements) notes TCC "fails to remember your choices" when the signature changes). Whether TCC attributes a helper spawned by Stream Deck to the helper or to Stream Deck.app is **unverified**.

**Failure modes the spike must check:** (1) tree hidden until `AXManualAccessibility`/`AXEnhancedUserInterface` is set, or only while Inspector runs; (2) meeting window minimized, on another Space, in compact view or with the toolbar hidden; (3) AXPress returns success with no effect, so always confirm by label flip within ~200 ms; (4) `kAXErrorCannotComplete` timeouts; (5) shortcut landing in the chat window instead of the call window; (6) `postToPid` not reaching a non-frontmost Teams, forcing a visible focus swap; (7) localized labels; (8) multiple `com.microsoft.teams` processes (use bundle id `com.microsoft.teams2`); (9) React menu items appearing asynchronously after the press; (10) TCC attribution and signature churn.
